# 评测方法论

> 目标：判断一次改动是「真的变好了」，还是「采样噪声」。
>
> 这个仓库不包含真实 holdout 与真实语料；`examples/eval_cases.sample.jsonl` 是合成的 10 条样例，只用于演示 schema。

---

## 1. 为什么不能只看单轮分数

配置类任务有三个天然噪声源：

1. **采样**：同一个 prompt 跑两次，回复长度和语气就不一样；
2. **judge 漂移**：LLM 裁判对「短句 + 半括号」有偏好，分数会随 rubric 微调跳；
3. **语料漂移**：不同阶段的聊天风格本来就在变（括号率可以从 47% 掉到 2%）。

所以流程是：

```
同一批 case × 3 轮 → 均值 ± σ → 用 mdd≈2σ 判断差异是否可分辨
```

小于可分辨下限的差异，一律写「无显著差异」，不写「变好了/变差了」。

## 2. 数据集分层

| 层 | 规模 | 用途 | 是否进发布门禁 |
|---|---|---|---|
| 冻结 holdout | 45 条（历史版本 20 条） | 回归 + 发布引用 | 是 |
| 回归集 | 50 条语料样本（滚动） | 发现新故障类/风格漂移 | 否（见 `POLICY_50.md`） |
| 离线规则集 | 78 项检查 | 单测/静态/接线 | 是 |
| 人工盲测 | 20 条 | 「像不像」的人判 | 否 |
| 认真话题触发 | 3 套离线 + 1 套 LLM | 该认真时认真 | 是（离线） |

冻结 holdout 的做法：

- `freeze_holdout.py --cases holdout.jsonl` 生成 freeze manifest（sha256、条数、分类分布）；
- 之后每次评测先 `--check`，文件被改过就拒绝跑；
- 发布说明里引用 freeze id，不引用「最新跑的一次」。

> 公开版只保留代码和 schema；真实 holdout 文件不发布。

## 3. 指标

### 3.1 LLM judge

`ops/eval/judge.py` 给每条回复打 1–5 分：

- `relevance`：有没有接住；
- `in_character`：像不像这个配置；
- `naturalness`：像不像示例对象聊天；
- `overall`：综合。

rubric 里明确写了：

- 短句、半括号、不接长篇情绪，是**允许**的；
- 长篇安慰、说教、AI 腔、正式承诺，扣分；
- 事实题编造具体时间/人名，直接低分。

### 3.2 确定性指标

不依赖模型，直接算：

- 长度分布（1–4 字 / 5–10 字 / 11+ 字）；
- 括号结尾率；
- 口癖频率（好好好/哈哈哈哈/捏/来着…）；
- 重复率（最近 N 条内相同/近似）；
- 贴纸配额；
- 与参考回复的相似度（`similarity_metrics.py`）；
- 视角错误（把「用户」说成「你」）。

这些指标进单测/门禁，不靠 judge。

### 3.3 人工校准

`judge_calibrate.py`：

1. `--build`：从分层样本里抽 20 条，生成 CSV/Markdown；
2. 人工填 `human_relevance / human_in_character / human_naturalness`；
3. `--compare`：算精确一致率与 ±1 一致率。

判定：`in_character` 的 ±1 一致率 < 70%，judge 不能单独作为验收依据。

## 4. 基准结果（历史示例）

45 条 × 3 轮，一次历史运行（私有数据，不可直接复现）：

| 指标 | 均值 ± σ | 可分辨下限（≈2σ） |
|---|---|---|
| 综合 | 4.25 ± 0.16 | 0.32 |
| 配置一致性 | 4.23 ± 0.19 | 0.38 |
| 自然度 | 4.53 ± 0.19 | 0.38 |
| 接住情绪 | 4.22 ± 0.13 | 0.26 |

解读：

- 自然度最高，说明「像示例对象说话」不是主要瓶颈；
- 配置一致性和接住情绪更低，说明「始终像同一个人」「该接的时候接住」更难；
- 单轮波动 0.5 很常见，所以必须跑 3 轮。

---

## 5. 50 条回归集的定位

`POLICY_50.md` 的核心结论：

- 50 条语料样本**不可按需生产**，做成门禁会无限期阻塞发布；
- 分布非平稳，不适合固定阈值；
- 需要人判，AI judge 有上限；
- 它只用于发现「新故障类」和风格漂移，不参与 pass/fail。

发布门禁仍然保留更硬的东西：78 项离线检查、冻结 holdout、P0/P1 回归、备份 verify。

## 6. 怎么跑（示例）

```bash
# 用合成样例跑一遍，确认环境能跑通
python ops/eval/bench.py --cases examples/eval_cases.sample.jsonl --runs 1

# 冻结集校验（需要真实 holdout，公开版没有）
python ops/eval/freeze_holdout.py --cases holdout.jsonl --check

# 人工校准
python ops/eval/judge_calibrate.py --build
python ops/eval/judge_calibrate.py --compare
```

> `bench.py` 需要 AstrBot 的数据库/配置路径，默认指向 `D:\demo` 占位路径；跑之前用 `DEMO_ROOT` / `DEMO_DB` 覆盖。

## 7. 经验教训

1. **先定「可分辨下限」，再谈好坏**。否则每次改完都能找到「变好 0.1」的理由。
2. **judge 只能当筛子，不能当裁判**。人工校准不过 70%，就不要拿它做发布依据。
3. **语料样本是消耗品**。50 条用完就没了，所以只做回归，不做门禁。
4. **接线测试比行为测试更早发现问题**。「测试全绿但功能没接上」是真实发生过的。
5. **一次只改一个变量**。配置、规则、provider 同时改，分数变化无法归因。
